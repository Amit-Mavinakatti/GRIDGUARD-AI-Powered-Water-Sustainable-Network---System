01 / Project overview

What is GRIDGUARD?

A demonstration of how water-network telemetry, simulation, and AI-assisted reasoning can work together in a monitoring workflow.

🗺️

Visual Network Model

Explore a simplified network made of junctions and connected pipe segments. Simulation controls let users test scenarios and observe changes in displayed readings.

📈

Telemetry & Anomalies

Pressure and flow concepts provide context for comparing a simulated network state with a baseline or expected behaviour.

✨

AI-Assisted Explanation

When the Gemini integration is configured and reachable, an AI response can help explain a supplied scenario. AI output is advisory and should be checked against the underlying data.

Project objective: make water-network monitoring concepts easier to explore through a practical, visual prototype—rather than claim a production-ready utility or certified detection system.

03 / AI implementation

AI supports interpretation—not instrumentation

The AI layer is intended to turn a supplied network scenario or diagnostic context into a readable explanation for a human operator or project evaluator.

🧩

Typical diagnostic workflow

  1. The user selects or creates a simulation scenario.
  2. The application gathers the context available to the diagnostic feature.
  3. The configured backend or integration sends a request to the Gemini model.
  4. The response is shown as an AI-generated explanation or suggested interpretation.
  5. The user compares that explanation with displayed telemetry and known simulation settings.
🔐

API key and privacy

For a deployed application, keep the Gemini API key on the server in an environment variable such as GEMINI_API_KEY. Do not commit secrets to Git or embed a private key in public client-side JavaScript.

AI requests may send the diagnostic context to the external AI provider. Do not submit credentials, private personal information, or sensitive infrastructure data unless authorised and appropriate safeguards are in place.

Important: an AI-generated explanation is not proof that a leak exists, nor is it a substitute for calibrated sensors, validated detection algorithms, domain-expert review, or field inspection. The actual features available depend on whether the API key, backend, network connection and relevant integration are configured correctly.
04 / User manual

How to use GRIDGUARD

Follow these steps to explore the interface safely and understand what the simulation is showing.

01

Open the project interface

Open the main project page in a modern browser. Use the project’s main dashboard link to access the monitoring view. Keep about.html beside the page that links to it, or update the link path if the files are in different folders.

02

Review the baseline network

Identify the junctions, connecting pipe segments and the values shown in the dashboard. Treat these as the current model or simulation context, not verified measurements from a real water system.

03

Run a scenario

Use the available preset leak controls or simulation controls to select a scenario. Watch for changes in node status, pressure/flow displays, summary metrics and event messages. Control labels can vary between project versions.

04

Adjust simulation settings

If available, adjust the severity/intensity control, unit selector or simulation refresh option. Change one setting at a time so you can observe which outputs respond to each change.

05

Read the telemetry carefully

Compare the displayed reading with its baseline, note which junctions or pipe segments are highlighted, and distinguish measured or calculated values from explanatory labels. A visual alert is only as reliable as the model and data behind it.

06

Request an AI explanation

If the AI diagnostic panel is enabled, ensure the backend and Gemini configuration are working, then run the diagnostic. Review the result as a suggestion, check it against the simulation, and do not treat it as a definitive engineering conclusion.

07

Export or record results

If telemetry export is enabled, use its export control to download a CSV and inspect the columns in a spreadsheet. Confirm the export fields correspond to the current simulation values before using them in a report.

08

Reset and repeat

Use the reset/clear control to return the simulation to its normal state, if provided. Try a different scenario and compare the resulting display. Clear any event history only after you have captured information you want to keep.

For a fair demonstration: describe the scenario you selected, what changed in the displayed telemetry, what the AI suggested (if used), and which parts are simulated. This makes the demonstration reproducible and avoids overstating the results.
05 / Developer setup

Running the Python backend

Use these instructions only if you are running the local Python backend from the project root and its dependencies are installed.

1

Open a terminal at the project root

Change directory to the folder containing backend/, simulation/ and requirements.txt.

2

Install dependencies (if needed)

Run python -m pip install -r requirements.txt from the project root.

3

Configure the AI key securely (if using Gemini)

In PowerShell for the current terminal session, set $env:GEMINI_API_KEY="YOUR_NEW_API_KEY". Replace the placeholder locally; never paste the real key into public code or documentation. If a key was exposed, revoke it and create a replacement.

4

Start the backend from the root

Run python -m backend.app. Starting from the project root helps Python resolve sibling project packages such as simulation. Exact startup behaviour depends on the current app configuration.

5

Open the frontend

Open the configured frontend page and ensure its API requests point to the correct backend address. If the browser blocks local requests or the UI reports connection errors, check the backend terminal and the frontend API base URL.

Configuration note: do not assume the backend is running just because the HTML page opens. AI diagnostics and backend-backed functionality require a running server, valid configuration, network access and any necessary API credentials.

07 / Responsible use

Scope, assumptions and limitations

Clear limitations are part of good engineering documentation and help visitors evaluate the project accurately.

What this prototype demonstrates

• A visual representation of a simplified pipeline network.

• Interactive exploration of configured scenarios and telemetry concepts.

• A possible workflow for pairing data-driven monitoring with AI-assisted explanation.

• Software integration concepts across a web interface, Python backend and supporting modules.

What it does not establish by itself

• Live connection to water utility infrastructure or physical sensors.

• Proven leak-localisation accuracy, validated performance metrics or guaranteed detection.

• Automatic control of pumps, valves or other physical equipment.

• Production-grade security, operational reliability or safety certification.

Future validation work: document the data sources and units; validate detection logic against labelled test cases; measure precision, recall and false-alarm rates; test sensor or OPC UA integrations in a controlled environment; add authentication, logging and key management; and have qualified domain experts review operational assumptions before any real-world use.
08 / Frequently asked questions

Quick answers

Does GRIDGUARD detect real leaks right now?

This page documents the project as a prototype. Unless real sensors, a verified data pipeline and validated detection logic have been connected, the interface should be treated as a simulation and demonstration.

Does the project require an AI API key?

Only the Gemini-backed AI feature requires its configured credentials. Core static documentation and any purely client-side interface can load without an AI key; backend-dependent functions may require separate configuration.

Why is the AI diagnostic unavailable?

Common causes include a stopped backend, a missing or invalid GEMINI_API_KEY, network connectivity, API access restrictions, an incorrect frontend API URL or a server-side exception. Check the backend terminal for the specific error.

Can this project be expanded?

Potential next steps include documented sensor interfaces, validated datasets, reproducible evaluation, calibrated thresholds, secure user access, robust telemetry storage and controlled integration testing. These should be implemented and tested rather than described as existing features before they are ready.
